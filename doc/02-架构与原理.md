# 02 · 当前架构与验证（v1.9.20 正式版 / v1.9.21 工作树候选）

现状：Windows v1.9.20 已正式发布，用户已确认一次安装版默认输出从 AirPods 发声；历史五轮失败仍保留。工作树 v1.9.21 是小精灵体验候选，已通过离线回归和编译；当前候选安装版完成一次真实断开，但随后连接核实失败，未有本候选的默认输出听音通过回执。候选尚未发布，最新状态以 `doc/04-项目进度.md` 顶部为准。
负责人：项目维护者与当前 Agent。
最后更新：2026-09-27。

## 组件
- `airpods_buddy.ahk`：托盘、窗口、设备列表、每设备状态机、配置、受限 RPC。
- `lib/AudioRouting.ahk`：Core Audio ACTIVE render/capture、IPolicyConfig slot 13、三角色读回、失败时条件回滚。slot 14 不是默认设备接口。
- `lib/BackgroundJobs.ahk`：独立目录、进程句柄、100 ms 非阻塞轮询、截止时间、超时终止、退出清理。
- `scripts/background-worker.ps1`：KS 蓝牙单次请求、反馈、更新下载等阻塞调用在子进程执行。
- `scripts/UpdateCore.psm1` / `update-swap.ps1`：已验证更新包、原子替换、原始哈希备份、启动健康标记及三秒存活复核、失败回滚。
- `scripts/RepairCore.psm1`：只读 Core Audio 端点诊断，以及显式指定单节点的恢复操作；绝不因端点数量增加宣称听音成功。
- `webui/`：资源内联 HTML。源文件与构建产物均纳入回归。
- `mac/AirPodsBuddyMac`：独立 Swift 产品，专属 macOS CI；不是 streamdeck helper。

## 连接状态
地址（12 位十六进制）是命令、优先级和任务主键；经精确 BTHENUM 节点绑定 ContainerId，再取得 MMDevice ID。名称仅展示，不再用名称关联音频端点。多个立体声候选时拒绝猜选。
每设备有 generation，新任务作废本设备的旧回调；只有最新连接任务拥有默认音频切换权。
API 接受请求 → 真实 Bluetooth link → ACTIVE render → 三角色默认设备读回 → 用户听音，是不同证据层。
`scripts/KsBluetooth.psm1/.cs` 在后台探测 KS BASICSUPPORT，再向精确目标发送 ONESHOT_RECONNECT/DISCONNECT；已 ACTIVE 的连接不重复请求。断开覆盖同 ContainerId 的 ACTIVE/UNPLUGGED render/capture，按驱动 filter 去重；UNPLUGGED 不代表控制链路已断。禁用或不存在端点不启用。
正常路径不调用 BluetoothSetServiceState，不卸装驱动、不重置无线电、不删除配对。麦克风开关只决定连接录音端点及切默认录音；关闭不再代表禁用 HFP 驱动。保留现有麦克风选择。
路由事务在切换前、三角色 HRESULT 和读回后均核实目标 ACTIVE；失活则条件回滚本次修改，不覆盖外部选择。watcher 也在读回后复核 ACTIVE。

## 连接/断开进度协议（v1.9.20 发布版）

`BuildDevicesJson()` 为每台耳机附加 `progress`：非终态含 `action`、`phase`、`step`、`steps`、`elapsedMs`、`phaseElapsedMs`、`phaseBudgetMs`；终态或无操作为 `null`。连接阶段为 `request → link`，必要时经过 `retry_wait → retrying`，再到 `audio`；断开为 `request → down`；重试 worker 内的取消先显示 `queued`，待原请求结束后才提交断开。第 N / M 步是阶段序号（连接 4、断开 3），不是已完成百分比；`phaseStarted` 只在真实阶段切换时更新。`phaseBudgetMs` 是该阶段一次有界核实的**观察窗口**，Windows 调用可能超过它，前端必须写明“非整体完成倒计时”，不能许诺总 ETA。

`webui/index.html` 使用既有品牌图标/小宠物与圆形主按钮的代码原生动效，不引入新位图：进度面板给出当前动作、原因、等待时间和阶段标记；列表/按钮保持同一状态。操作请求到首次后端快照之间可短暂用本地占位，旧后端缺少 `progress` 时按其 busy 状态降级，不能在超时后凭前端计时宣告成功。终态结果卡持留到设备状态变化；`ready` 文案仅表示无声预检与默认路由核实完成，仍要求用户试听。标题用 `aria-live`，连续秒数不反复播报；`prefers-reduced-motion` 停止重复动画。

连接请求提交阶段按钮禁用；其余连接核实中可取消/同目标断开；重试 worker 进行时后端先显示排队，再对同目标提交断开，并用代次/epoch 防旧回调越权。断开核实中按钮禁用，后端全局 `busy` 对重复请求返回忙碌而不并发提交。阶段观察与 UI 显示均不新增 KS 请求、全局蓝牙重置或配对操作。v1.9.20 发布前的完整离线、界面截图和安装版验收见 `verification/2026-09-27-progress-frontend/`、`verification/2026-09-27-release-public/`；不能把发布前快照误读成现状。

## 右下角小精灵生命周期（v1.9.21 未发布候选）

连接和断开请求被 `DoAction` 接受后统一显示独立的 `pet_built.html` 弹窗；`busy` 等未接受请求不闪现。宠物创建通过一次性定时器排在主页面 RPC 返回之后，避免在 WebMessage 回调内同步等待第二个 WebView2 控制器；复用主环境，只有控制器对象与初始化标志均就绪才使用 GUI，初始化中仅保留最新请求。弹窗每 500 ms 只读同一设备操作的 `DeviceProgressJson`/状态，显示动作、真实阶段及已等待时间；取消排队和托盘多设备断开按队列整体终态展示。进行中没有固定 9 秒消失计时；明确终态后停留约 2.5 秒再退出，新操作先取消旧淡出/隐藏定时器；若 WebView2 尚未就绪，终态停留在 `petready` 后才计时。新直接操作被接受时让旧批量断开队列票据失效，防止剩余设备被旧意图断开。连接中链路失效/未知终态显示失败，不永久加载。失败或未确认不冒充成功，播放预检完成仍提示用户试听。

`webui/pet.html` 的 `setProgress({state,phaseText,elapsedMs})` 只换文字，不重置当前动画帧；等待帧使用姿态桥接，终态只播一次，减少动态效果时停用循环。宠物不改变蓝牙 KS 请求、路由或设备设置；对应离线回归见 `tests/pet_lifecycle_test.py`、`tests/pet_ready_race_test.py`、`tests/pet_reentrancy_test.py`、`tests/pet_popup_test.cjs` 和 `verification/2026-09-27-pet-reentrancy/`。

## WebView 与资源
主页面固定为 `https://app.airpods.local/index_built.html`，宠物固定为同域 `pet_built.html`，通过 WebView2 虚拟主机映射到本地内嵌资源。
两页分别校验精确来源，阻止其他顶层导航/新窗口；openurl 只接受项目 GitHub HTTPS 地址。网页不提供更新 URL，不获取机器人凭据。
不再使用 NavigateToString：真实验证发现它的 NavigationStarting URI 是内部 data URL，直接按 about:blank 拦截会白屏。
编译资源释放到 `%TEMP%/AirPodsBuddy_app/<版本>-<PID>-<启动GUID>`；各文件缺失时单独重新释放，避免覆写正在加载的 DLL。清理仅针对本应用、七天前且所属进程已退出的目录。
Runtime 缺失只记日志/托盘提示，使用现有 Edge 兜底；不自动下载安装，不弹错误对话框。

## 持久化与反馈
设置读取—修改—原子替换在 AHK critical 区域内；失败保留旧文件并传回 UI。优先级启动时先初始化路径再加载。
反馈只从宿主发送一次，HTTP 完成不等于成功；必须收到 JSON errcode=0。附带日志由用户勾选，附件失败与文本送达分别报告。

## 构建、部署、测试
`powershell -File scripts/build-deploy.ps1` 仅构建；`-Deploy` 才替换桌面常驻目录。始终先构建前端并校验新包，再停精确路径的旧进程；不是 taskkill 所有同名程序。
构建清单含版本、源码哈希、exe 哈希。部署 / 更新通过真实 WebView 导航后的健康标记及存活检查验收；失败使用原始哈希核对回滚。
完整离线入口：`python tests/run_suite.py`（不连接硬件、不部署）；KS 策略故障注入 `powershell -NoProfile -File tests/ks_backend_test.ps1`。
分项测试入口：`python tests/run_behavior.py airpods_buddy.ahk`、`python tests/run_state_tests.py`、`python tests/run_ahk.py tests/audio_routing_test.ahk`、`python tests/run_ahk.py tests/background_job_test.ahk`、`node tests/rpc_test.cjs`、`powershell -File tests/windows_regression.ps1`。
真实耳机测试 `tests/live_audio.py` / `tests/wasapi_probe.py` 只在耳机在场时运行，不放进无人值守 CI。

P0 同钟诊断：`KsBluetooth.cs` 的 `KsTrace` 将每次 KS 请求的 UTC FILETIME 起止、property、精确目标端点和 HRESULT 透传至 worker 与应用日志；它只记录，不增加请求。`tests/p0_timeline.py` 默认只读，以同一 FILETIME 时钟按 500ms 采样目标链路、播放端点状态和三个默认输出角色，并读目标 PnP/System 事件；显式 `--action connect` 或 `--action cycle` 才调用现有源码流程，后一种最多一轮且第一步失败即止。采样数据保存在 `verification/2026-09-26-timeline/`，不进入日常安装版自动遥测。一次真实断开耗时约24秒，旧9秒窗口出现假失败；v1.9.20 已将核实窗口延至约30秒，不额外发KS请求。连接稳定性仍独立验收。

断开终态：`GetLinkState` 明确区分已连接1/已断开0/查询未知-1；只有0且同一ContainerId下worker列出的目标render/capture端点都明确非ACTIVE，才通知断开成功。枚举失败、目标ID缺失、仍ACTIVE都继续观察直至截止，不能冒充成功。读取采样器逐项记录耗时；蓝牙/音频API可能阻塞，样本数量不能代替时间覆盖率。单轮真机对照通过不代替五轮与听音。

## KS 请求接受后的有界恢复
仅用户当前连接事务内，链路或音频核实耗尽时等待 15 秒，最多再发一次同目标请求，两阶段共享同一个预算。HRESULT 失败/能力不足不重试。等待结束若链路与精确播放端点都已就绪，则只核实路由，不重复请求。每个 timer 与回调检查代次、路由所有权和用户操作 epoch；新操作取消旧恢复，不进行后台无限重连。

等待和重试中 UI 持续显示状态及取消按钮。若用户在重试 worker 执行时要求断开，则取消核实并排队同目标断开，worker 结束后执行；更晚的新操作可使旧队列失效。默认输出只有当前有效事务可修改。
