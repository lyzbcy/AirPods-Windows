# 03 · 技术方案

> 读这份文档的时机：做技术决策、升级依赖、或想知道"为什么这么选"。

## 2026-09-25：连接抢占与双端点修复预研（未实施）

现状：源码已有录音端点查找与 `IPolicyConfig::SetDefaultEndpoint` 切麦链，但尚无播放端点校验/切换。连接返回成功并不保证播放与录音默认端均指向目标设备。应先在 `AudioVerifyTick` 后分别读默认播放/录音端点 ID，按设备 PnP 身份匹配；只有端点已激活、且用户选择对应模式时才提供“一键切换”，避免强抢用户当前音频路由。

方案比较：
- [AudioDeviceCmdlets](https://github.com/frgnca/AudioDeviceCmdlets)：MIT，可按端点 ID 获取与设置默认播放/录音及通信设备；但需另带 PowerShell 模块/进程，当前尚未量测打包体积与本机安全软件拦截率。
- [NirCmd](https://www.nirsoft.net/utils/nircmd.html)：有 `setdefaultsounddevice` 命令，但按显示名选择可能歧义；官方许可仅允许免费完整原样分发，不适合直接内嵌为可抽取的资源，体积亦未量测。
- 复用现有端点 ID + `IPolicyConfig` 链：不加新依赖，优先做本机验证；接口行为须在实际 Windows 版本回归，不把“已发出切换”当作“已切成功”。

“删除设备→重新配对”不能当作无条件一键自救：[Windows `UnpairAsync`](https://learn.microsoft.com/en-us/uwp/api/windows.devices.enumeration.deviceinformationpairing.unpairasync?view=winrt-28000) 会移除既有配对，[微软配对流程](https://learn.microsoft.com/windows/uwp/devices-sensors/pair-devices) 需要设备可发现及配对交互。先完成只读检测、非破坏性断连/重连与端点重选；真正移除配对须另做交互状态机与真机验证，不能在无头测试中假称成功。

验收矩阵：HFP 开/关 × 播放端已正确/错误 × 录音端已正确/错误 × 设备离线/在线；记录操作前后端点 ID、连接链路位与失败码，耳机在场时逐格核验。当前研究未改变运行路径。

## 前端构建链

`webui/index.html`（源码，引用 `assets/` 相对路径图片）
→ `webui/build_ui.ps1`（把 7 张图片转 base64 data URI 内联）
→ `webui/index_built.html`（~894KB）
→ `FileInstall` 内嵌进 exe → 运行时释放到 `%TEMP%\AirPodsBuddy_app\`
→ `NavigateToString()` 整串加载。

**约束**：
- `NavigateToString` 内容上限 2MB（当前 894KB 字符 ≈ 1.79MB UTF-16，**接近上限，
  以后别再加大图**；超了就得改用 `SetVirtualHostNameToFolderMapping` 方案）
- 图片改动后必须重跑 build_ui.ps1 再编译，否则 exe 里是旧图

## 关键设计决策记录

| 决策 | 备选 | 理由 |
|---|---|---|
| `NavigateToString` + base64 内联 | 虚拟主机映射本地文件 | 单文件分发优先；代价见上 |
| 全局 OnError 静默 + 日志 | 保持 AHK 默认弹窗 | 用户被"奇怪报错弹脸"吓过，明确要求不弹窗 |
| WebView2 创建重试 3 次 | 单次 | 本机安全软件会瞬时拦截（0x800704C7） |
| 关窗=隐藏到托盘 | 关窗=退出 | 工具型常驻设计；`Persistent` 是关键 |
| 日志按天分文件+7天清理 | 单文件追加 | 便于按日期排查，防无限膨胀 |
| 音频方案 A2DP+HFP 默认 | 纯 A2DP | 麦克风可用优先；上游脚本支持切换 |

## 性能与资源

- 空闲占用：~30MB（AHK）+ WebView2 浏览器进程组（共享 UDF，多实例便宜）
- 启动到界面可见：<2 秒（含 WebView2 环境创建）
- 蓝牙操作：连接 2-8 秒（受系统蓝牙栈影响，重试机制兜底）


## 音频默认设备切换（v1.9.16，2026-09-26 上游+SoundSwitch 调研定稿）
- 接口：CPolicyConfigClient {870af99c-…} / IPolicyConfig {f8679f50-…}
- vtable（0 起数，实测+SoundSwitch/AudioSwitcher 布局交叉验证）：
  [13]=SetDefaultEndpoint(PCWSTR, eRole) 双参；[14]=SetDefaultDevice(PCWSTR) 单参
  （此前 GPT 用 13 传双参在这台 Win11 恒 E_INVALIDARG 的原因：端点过渡态+两次实测
  均失败；正确做法是 14 单参为主 + 13 逐 role 为辅，任一成功即算切上）
- 三个 role 必须全设：eConsole/eMultimedia/eCommunications——缺 eCommunications
  时微信/游戏语音仍走旧设备（上游 ChromuSx AudioEndpointRouter 同款）
- 端点匹配：render 方向 NOT LIKE '%Hands-Free%' 优先（AirPods 同设备暴露
  Stereo 与 HFP 两个 render 端点，模糊匹配会选错；上游打分 -50 同理）
- 等待：播放端点 12s（250ms~1.5s 粒度轮询，对齐上游）；切完只记日志+toast，
  回读验证（GetDefaultAudioEndpoint）留作后续增强
- 调研来源：ChromuSx/BluetoothDeviceConnector(MIT) AudioEndpointRouter.cpp、
  SoundSwitch(PolicyClient.cs, 只学做法)、AudioSwitcher(MS-PL)、
  codemachine.com 默认设备机制文
