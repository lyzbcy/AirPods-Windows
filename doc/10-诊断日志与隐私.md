# 10 · Windows 诊断日志与隐私

现状：v1.9.22 工作树候选，v1.9.21 已发布版保持不变；本页描述候选的日志协议。
负责人：项目维护者与当前 Agent。
最后更新：2026-10-09。

## 目标与边界

10 月 1 日的真实反馈只有“列表里找不到耳机”。旧日志能看见启动、添加与刷新，却分不清未在 Classic API 中发现、筛选遗漏、枚举错误和前端 JSON 错误。新增诊断用来确定故障阶段和下一条排查路径，不保证从一份日志确定所有驱动／耳机侧根因。

实现入口：`lib/Diagnostics.ahk`；生产接点：`LogMsg`、`FindAllAudioDevices`、`SendIssueAsync`、`GatherLogTail`、`BuildIssueLogFile`。诊断采集自身不修改生产列表筛选、连接后端、配对、默认音频或无线电设置，不发 inquiry／KS 请求，不播放或录音。

## 日常日志

- 启动：软件版本、Windows 版本／构建号、进程位数、是否编译版、`diagnosticSchema=1` 与随机会话标签。不再记安装绝对路径。
- 设备发现：枚举模式、status、返回／接纳／筛除数量、未知类别／非音频筛除数量、已连接／remembered／authenticated 数量、首个／末次枚举错误码、刷新详情失败数量与最近错误码、耗时。
- 接纳候选：最多 16 条，记录本会话 `device#N`、名称提示类别 `airpods/pro/max/beats/other`、Class of Device 与三个布尔状态；名称提示不是用户已确认的型号。未接纳设备只给筛除数量，不逐台展示非音频设备。
- 同一状态不每四秒重复写入：结果／状态变化写一次，五分钟心跳写一次；耗时变化不触发重复。每条消息上限 4096 字符，滚动日志仍保留七天。
- RPC 只记命令、请求序号、参数数量；连接／断开／移除用本会话目标编号。自定义优先级只记条目数。前端错误只记 `list_json_parse` 或 `script_error` 与长度，不附原始 JSON／脚本 payload。

`status=no_match error=259` 表示该次查询无匹配；`api_error` 表示查询错误／不可用；`partial nextError=...` 表示结果不完整。空列表不是“蓝牙已关闭”或“用户没配对”的充分证据。若采集自身失败，记录 `diagnostic_error`，不让日志错误影响原列表操作。

## 用户勾选附日志时的一次性快照

只有 `wantFile=true` 才执行 `DiagnosticCollectFeedback`，并把同一快照交给摘要和文件两条路径。

1. 比较 `authenticated` 与 `cached`（authenticated + remembered + connected）两次只读 Classic 枚举；不启用未知设备搜索，也不启用 inquiry。额外快照最多处理 128 条，超出写 capped／partial，不伪称完整结果；逐台候选细节仍最多 16 条。
2. 只记可见 Classic 无线电数量和 API 错误码。`power=unverified` 明确表示没有读取／证实蓝牙开关；数量不替代电源状态。
3. Core Audio 仅读取播放／录音端点四种状态数量、Apple 名称提示数量、三个默认角色的匿名编号；不激活音频流、不切默认、不录音、不播放。
4. 输出 `observation`：Classic API 错误、不完整结果、较宽枚举发现候选而生产筛选没有、候选筛选为空、没有缓存 Classic 候选、已有候选。所有 observation 均附 `notRootCause=true`，只是下一条排查路径。

这些 Classic API 不覆盖 LE-only 设备；没有匹配可能包含未配对、LE 路径或系统缓存问题等情况，日志必须保留这层不确定性。

## 脱敏与数据最小化

- 蓝牙地址、端点 ID、ContainerId／GUID 用**仅当前进程有效**的编号替换，不使用稳定设备哈希，不把映射写入文件。随机会话标签在进程内固定，重启重新生成；跨会话编号不视为同一台设备。
- 不输出真实设备自定义名；本次枚举读到的名字仅暂存在进程内供脱敏匹配，诊断只输出固定类别。
- 个人磁盘路径、UNC 路径、PnP 实例 ID、邮箱、常见手机号、IP、SID、Bearer／JWT 和带 key/token 等字段的值均处理；原始 RPC、自定义优先级和旧前端 JSON 错误等自由内容丢弃。技术状态／HRESULT 保留。
- `LogMsg` 在本地落盘前统一脱敏；脱敏器错误时只写通用失败标记，不回退为原文。此前已经存在的旧日志不就地改写，但**反馈导出时重新脱敏**，避免把昨日旧路径／地址上传。
- 附件不再含源文件绝对路径标题。今天／昨天各保留最多约 48K 字符尾段，诊断快照与版本头部单独保留；摘要按昨日→今日取最近 50 行，快照放最后，让字节预算裁剪优先保留当前证据。
- 用户主动填写的描述和联系方式仍按其意图发送，不作为诊断隐式采集。取消附日志时只发这些主动填写内容，不读日志、不采集设备快照、不创建附件。反馈 UI 明示脱敏范围。
- 不新增自动遥测、后台上报、网络地址查询、用户／计算机名、系统安装软件清单、序列号、录音或使用内容采集。

## 验证与维护

`python tests/diagnostics_test.py` 运行生产脱敏器、格式化／去重、异常分支与旧日志导出，使用合成设备与文件。`python tests/feedback_consent_test.py` 验证勾选前后采集次数与两条反馈路径。两套均加入 `tests/run_suite.py`，不联网、不触碰真实设备。

`verification/2026-10-02-private-diagnostics/read_only_probe.py` 是本次人工触发的只读本机取证，不进无人值守 CI；原始脱敏结果、耗时、构建与回滚均在该目录。它没有重放 10 月 1 日用户的设备，也不是对那位用户根因的证明。

新增日志字段应优先使用固定枚举和技术状态。增加自由字符串前必须补“合成私人信息不得出现在输出”的负向测试，并检查本地落盘、文本摘要、附件三个边界。

Win32 字段与句柄释放依据：[设备搜索参数](https://learn.microsoft.com/en-us/windows/win32/api/bluetoothapis/ns-bluetoothapis-bluetooth_device_search_params)、[无线电枚举](https://learn.microsoft.com/en-us/windows/win32/api/bluetoothapis/nf-bluetoothapis-bluetoothfindfirstradio)。可见无线电不作为电源状态的判断。

## 音频路由变化诊断（10 月 9 日）

仅观察到状态摘要变化时记录 `route observation`，含 `reason`（ready/default_changed/endpoint_inactive/endpoint_missing/query_failed）、端点状态数值、三默认输出角色匹配位掩码与失败角色，不记录角色的新设备 ID。只读枚举前后复核 ACTIVE，查询失败返回 unknown、不把 ready 状态改成 audio_lost；已证实失活／改路由仍由用户手动处理，不自动抢回输出。本轮麦克风功能改动单独见 doc/11。启动时清理七天前日志的既有逻辑原样保留，无新定时清理／容量配额。

勾选附日志时对最多三个去重的默认录音端点只读 session state，附 observedActive=1/0/-1、complete=unverified。最多 128 个会话，无 PID／应用名、无录音或流启动，0 不证明没有独占或未枚举到的录音。
