## 目标与边界

历史 2026-10-19 beta.1 设计背景：用户提出 Pro 3、多应用麦克风争用、希望支持入耳检测和通透 / 降噪控制。本增量只建立独立 AAP 控制实验室，不改主程序连接 / 切麦后端，不把经典蓝牙 HFP 音质限制与 AAP 控制混为一谈。主程序 APP_VERSION 保留 1.9.23 候选；Beta 自有 csproj 版本 1.10.0-beta.1，独立 exe 与配置目录。

结构：`beta/AirPodsBuddy.Beta/Protocol.cs` 纯协议；`Session.cs` 可注入 IChannel 的会话；`Driver.cs` SetupAPI 只读枚举与异步句柄；`Program.cs` WinForms 与诊断；`beta/tests` 无 NuGet 测试控制台。遵守根 SKILL / AGENTS 的发布、桌面测试和配对红线。

## 协议与来源

1. [librepods AAP Definitions](https://github.com/kavishdevar/librepods/blob/main/docs/AAP%20Definitions.md)：公开抓包协议事实。文档样本为 Pro 2 USB-C / FW 7A305；**不是 Pro 3 验证**。
2. [MagicAAP 官方帮助](https://help.magicpods.app/fun-magicaap/)：Windows 高级功能依赖额外内核驱动。实验包不含、不安装该驱动，不自动改变系统设置。
3. [AirPodsWindows MagicAAPClient](https://github.com/YimingZhanshen/AirPodsWindows/tree/main/Source/Core)：兼容性 ABI 线索，不作为真机成功证明。该实现列出的首选 GUID 存在混淆，**未直接采用**。
4. 官方 `https://magicpods.app/utils/magicaap.zip` 仅在内存中检查 INF 和 GUID 引用，未安装或运行。ZIP SHA256 应与验证目录收据及官方说明核对。INF 中 `74ec2172-0bad-4d01-8f77-997b2be0722a` 是 BTHENUM 服务 UUID；官方 sys 中实际 WDF 注册引用 `9eec98bb-3c54-45d4-a843-7900c4635e08`（偏移 12080，注册调用引用）才用于当前 SetupAPI 枚举。该版本 ABI 的读写及 Pro 3 兼容仍待真机验证。

没有复制第三方实现代码或捆绑驱动；根据协议事实独立编写。第三方参考项目有 GPL 许可，后续若引入实现代码必须先评估许可，不将“公开可见”当作任意再许可。

消息：L2CAP PSM 0x1001（由已有驱动负责传输），16 字节 handshake，10 字节 subscribe。噪声控制 / 上报为 **11 字节** `04 00 04 00 09 00 0D <1..4> 00 00 00`，不是旧 noise_mode.ps1 的 12 字节；旧托盘原型本次未改、未宣称能用。入耳消息 8 字节，主副各 00 入耳 / 01 未入耳 / 02 在盒内；主副不等于左右，主耳角色会变化。H2 能力包仅用户勾选时发送，行为影响需要实测。

解析器按驱动 ReadFile 返回的 SDU / 包批次处理，有界 4096 字节。支持连续的已知入耳、模式、跳过合法长度的电池记录；未知包、不完整包、非法值不产生状态，也不从未知 payload 中扫描“伪状态”。**跨两次 ReadFile 拆包不重组**，当前假设驱动保留 SDU 边界；必须在真机确认。若兼容驱动分片，先补有长度定义的 framing，不靠盲扫敏感 metadata。

## 会话与成功语义

用户明确选目标才 CreateFile，重新枚举拒绝已消失的路径。只使用读写及 overlapped 标志，不获取音频设备、不播放、不采集麦克风。握手 / 订阅写入限时 4 秒；单接收循环；模式命令串行。模式完成写入之后才布置等待槽，因此写前缓存匹配报告不能通过；响应极快可能保守地被漏判成超时，不反向假报成功。协议没有事务 ID，匹配表示“观察到目标状态”而非本次命令 ACK。

回读不一致单独显示；超时 / 失败关闭会话并取消未完成 IO，不自动重试。关闭或 EOF 清状态、清等待槽，旧 session 事件不更新新 UI。入耳只观察、不接媒体键；无报文不自动认定摘耳或断开。UI 显示每类上报年龄，不把旧值冒充实时。

型号只按 OS 名称推测并保留来源，默认无硬件认证；手动覆盖可纠正名称。未知型号不开放模式，H2 自适应另外要求用户显式勾选。策略表只是试验门控，不能把用户填写型号当硬件证明。

## 2026-11-25 晚：Winsock L2CAP 定论

完整证据与来源在 [14 · 第 2 节](14-竞品对标与高级能力路线.md)。

- `tools/noise_mode.ps1` 那条 Winsock 原型从原理上走不通：微软蓝牙栈的用户态 Winsock 只支持 `BTHPROTO_RFCOMM`，L2CAP 只能由内核 profile 驱动通过 BRB 提交。实测现象是 `socket()` 成功、`connect()` 报 `WSAENETDOWN (10050)`，与适配器品牌无关，Windows 11 24H2 也一样。[官方文档] [issue 用户报告]
- 本机补测（2026-11-25 晚，只读、未向耳机寻呼）：32 位和 64 位进程里 `socket(AF_BTH, SOCK_STREAM, BTHPROTO_L2CAP)` 与 `BTHPROTO_RFCOMM` 都返回 `WSAEAFNOSUPPORT (10047)`，而 `netsh winsock show catalog` 里列着 `MSAFD L2CAP [Bluetooth]` 和 `MSAFD RfComm [Bluetooth]`，蓝牙适配器在线且可连接。也就是说这台机器上用户态蓝牙套接字整体不可用，调研里建议的「WinSock 探测」在本机用不了。原因未查，可能与通用适配器的微软通用驱动有关。[推测]
- 因此本机「0 个 AAP 接口」不是这台机器的特殊情况：不装内核驱动，任何 Windows 机器都是 0 个。换适配器、换厂商驱动、改注册表、换 Windows 版本都没有用。
- 所有做成的竞品都靠内核驱动：MagicAAP、NTPodsAAP、SoundStage 是 KMDF profile 驱动（测试签名，需 Test Mode）；WPods 靠 WinUSB 接管适配器加 usbip-win2。
- MagicAAP 官方驱动未签名；社区签名版自 2026 年 4 月安全更新后默认不被信任。本项目不引导用户去关驱动策略或开 Test Mode。
- 实验包保持现状：没有可信、已签名的控制通道就不发任何命令，界面如实说明原因。`beta/` 里已独立实现的协议编解码、会话串行、回读与超时逻辑是将来接上签名驱动后可以直接复用的部分。
- 唯一可以考虑的无前提增强：用户已经自己装好并正常运行 MagicAAP 时复用它的设备接口。接口无文档、通道独占，只能做成默认关闭的实验性选项，并且不随包分发该驱动。

## 1.10.0-beta.3 视觉与能力边界
