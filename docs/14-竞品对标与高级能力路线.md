# 竞品对标与高级能力路线

现状：稳定；结论来自 2026-11-25 的三份带来源调研 ｜ 负责人：项目维护者 ｜ 最后更新时间：2026-11-25

目标：把最常用的 Windows 一键连接做稳做快；把控制通道与音频通道分开看，逐步实现 AirPods 高级能力。竞品 README 是作者的能力声明，不是本机真机验收。本文每条事实带可信度标签：[官方文档]、[源码确认]、[作者声明]、[issue 用户报告]、[社区实测]、[推测]。

## 0. 结论速览

1. **降噪 / 通透 / 自适应在 Windows 上必须有内核驱动。** 微软蓝牙栈的用户态 Winsock 只接通了 RFCOMM，AAP 用的 L2CAP PSM 0x1001 只能从内核提交，和适配器品牌无关。做成这件事的项目全部依赖内核驱动，而且都是测试签名。[官方文档] [源码确认]
2. **用耳机麦还保持高音质，同样必须有内核驱动。** 唯一绕开 HFP 的办法是 AAP 的 0x58 麦克风流（AAC-ELD）加一个虚拟麦克风。[源码确认]
3. **连接触发方面我们已经在最优路线上。** KS `ONESHOT_RECONNECT` 加 HFP 优先，与 ToothTray（BSD-2）和上游（MIT）的独立实现一致；WinRT / RFCOMM 兜底不值得做。[官方文档] [源码确认] [社区实测]
4. **收费竞品的招牌功能现在正被 Windows 卡着。** MagicAAP 官方驱动未签名、要开 Test Mode；社区签名版自 2026 年 4 月的安全更新起默认不被信任。谁先有正规签名的驱动，谁就拿到这块市场。[作者声明] [官方文档] [issue 用户报告]

## 2. 历史遗留问题一：降噪 / 通透 / 自适应

### 为什么不装驱动做不到

- 微软文档：Winsock 蓝牙套接字支持的是 `BTHPROTO_RFCOMM`；L2CAP 由内核 profile 驱动通过 BRB 使用。[官方文档]
- 实测现象：`AF_BTH + BTHPROTO_L2CAP` 的 `socket()` 成功，`connect()` 失败 `WSAENETDOWN (10050)`，Windows 11 24H2 上同样如此。[issue 用户报告]
- 没有任何项目发布过「换 Intel / Realtek 适配器就能用」的兼容性矩阵；换适配器或换厂商驱动不改变结果。[推测，基于检索无结果]
- WinRT 的 `Windows.Devices.Bluetooth.Rfcomm` 只有 RFCOMM；AAP 在 SDP 里是 L2CAP 服务，不能走 RFCOMM 承载。[官方文档] [issue 用户报告]
- 本机补测：32 位和 64 位进程创建蓝牙套接字（L2CAP 与 RFCOMM）都返回 `WSAEAFNOSUPPORT (10047)`，适配器在线；未向耳机发起任何请求。所以「用 WinSock 探测做诊断」的设想在这台机器上不成立，用户态没有可用的通道。[本机实测]

### MagicAAP 驱动的现状（2026-11）

- 架构：绑定在 BthEnum 为 AAP 服务创建的设备节点上的函数驱动，用 `GUID_BTHDDI_PROFILE_DRIVER_INTERFACE` 加 `BRB_L2CA_OPEN_CHANNEL`；同构开源实现 NTPodsAAP 与 SoundStage 的 INF 匹配 `BTHENUM\{74ec2172-0bad-4d01-8f77-997b2be0722a}`。[源码确认]
- 官方版未签名，必须开 Test Mode 并关 Secure Boot，作者自己警告只适合做好重装系统准备的高级用户。官网仍写着「如果你能给官方驱动签名请联系我」。[作者声明]
- 社区版用变通方法签名，可能被 Defender 或反作弊标记；2026 年 4 月安全更新后交叉签名驱动默认不受信任，官方称关闭该策略会降低设备安全性；2026-11-17 仍有装完重启后策略被重新启用的未解决 issue。[作者声明] [官方文档] [issue 用户报告]
- 第三方可以在用户已安装时复用其设备接口（AirPodsWindows 就这样做），但接口无文档、通道独占，且未找到作者对第三方复用的授权。[源码确认] [推测]

### 协议事实（可独立实现的部分）

| 项目 | 事实 | 可信度 |
|---|---|---|
| 位置 | L2CAP，PSM 0x1001 | [作者声明] |
| 设置模式 | `04 00 04 00 09 00 0D <01..04> 00 00 00`：01 关闭、02 降噪、03 通透、04 自适应；耳机回同样的包 | [作者声明] [源码确认] |
| 自适应强度 | `04 00 04 00 09 00 2E <0..100> 00 00 00`，只在自适应模式生效 | [作者声明] |
| 前置条件 | 必须先发 0x4D 特性包，否则设自适应会被改回别的模式；掩码位各家取值不一 | [作者声明] |
| 新固件切「关闭」 | 需要先启用 Off listening mode（0x34） | [作者声明] |
| 支持强度的型号 | AirPods 4 (ANC)、AirPods 5、Pro 2、Pro 3；另有实现加上 Max 2 | [源码确认] |

这些报文已经独立实现在 `beta/` 的 `Protocol.cs`，没有任何真机回读证据。

### 路线选择

| 路线 | 能得到什么 | 代价 | 结论 |
|---|---|---|---|
| 正规签名驱动（EV 证书 + 微软 attestation / WHQL） | 完整的降噪控制，且比竞品更安全可用 | 证书与认证成本、驱动开发与维护、需要公司主体 | 建议作为中期目标，这是收费竞品目前过不去的坎 |
| 复用用户已装的 MagicAAP | 用户自行承担风险后可用 | 接口无文档、可能与 MagicPods 抢通道 | 只做成默认关闭的实验性选项 |
| 接管适配器（WPods 路线） | 不需要自家驱动 | 装第三方内核驱动、全部蓝牙流量走用户态代理、重启后可能丢失蓝牙 | 不做 |
| 无驱动的 BLE 广播 | 电量、入耳检测、弹窗 | 较新固件可能加密广播 | 值得做，见路线图 P2 |
| 诚实降级 | 控件置灰并说明原因 | 无 | 当前默认 |

## 3. 历史遗留问题二：用耳机麦后音质差、容易掉

### 原因

- 微软文档：Classic 蓝牙使用耳机麦克风时走 HFP，采集与播放都是单声道，A2DP 与 HFP 不能同时成立。[官方文档]
- 本机实测 HFP 采集是 1 声道 8000Hz，属于窄带回退；能否协商到 16kHz 的 mSBC 取决于适配器、驱动和耳机三方，没有强制开关。[官方文档]
- 每次开关麦都会触发 A2DP 与 HFP 互切，多应用争用时反复切换，期间有间断并可能掉线。[官方文档] [推测]
- AAP 麦克风流与 HFP 同时进行会让 AirPods 掉链路。[源码确认]

### 竞品怎么绕

- NTPods、WPods、LibrePods 的 PR 用的是同一组报文：发 19 字节 `START_AUDIO`，收 0x58 上行包，用 AAC-ELD 解码后写入虚拟麦克风。NTPods 用两个测试签名驱动；WPods 靠接管适配器加虚拟 USB 麦。[源码确认]
- 即使做到，用麦时播放仍可能是单声道（NTPods 作者自述），只有 WPods 声称 H2 型号能保持立体声，且项目很新、稳定性问题未关闭。[作者声明] [issue 用户报告]
- SoundStage 与 MagicPods 都没有解决，官方建议都是「输出走 Stereo，另用一个麦」。[作者声明]

### Mac 为什么听起来正常

- Apple 自己的文档承认：蓝牙切到用麦的模式后音频质量会下降，直到不再使用麦克风。[官方文档]
- 2024 年固件为 AirPods Pro 2 带来通话语音隔离，提到 16-bit / 48kHz 音频；2025 年固件为 H2 机型带来录音棚级录音，并称通话语音更自然。处理在耳机与 Apple 设备之间完成。[官方文档]
- 所以 Mac 的优势来自 Apple 私有的宽带通话通道和语音隔离，加上 macOS 常直接用电脑自带麦；这不等于「用耳机麦还保持 AAC 立体声」，Windows 上无法等价复制。[社区实测] [推测]

### 零驱动能做的（第①层，建议现在就做）

- 引导通话软件使用电脑麦克风，耳机保持 A2DP 立体声；这同时消除了互切和大部分掉线。
- 提供「禁用此耳机的免提」开关（默认关）：调用公开 API `BluetoothSetServiceState` 对单个已配对设备停用 Hands-Free，耳机麦不可用但播放始终是立体声，可逆。MagicPods 与 WPods 都有这个开关。[官方文档] [源码确认]
- 如实披露：耳机麦在这台机器上是 8kHz 电话音质，改不了；不能替别的应用选麦，只能引导或经同意改默认设备。

第②层（虚拟麦克风驱动）与第③层（接管适配器）都和「不装内核驱动」冲突，暂不做。

## 4. 连接触发：证据排序

| 排序 | 方式 | 证据 |
|---|---|---|
| 1 | 对 HFP 端点过滤器发 KS，再等 A2DP 激活 | 本机 4 次成功；上游与 btcom 都是 HFP 在前 [源码确认] [社区实测] |
| 2 | 对容器内所有过滤器发 KS，HFP → A2DP | ToothTray 的做法，多人确认可用 [源码确认] |
| 3 | `BluetoothSetServiceState` | 会安装对应驱动；有「已连接但没声音」的报告 [官方文档] [社区实测] |
| 4 | WinSock SDP 查询或 `connect()` 探测 | 没有能带出音频端点的证据；本机连套接字都创建不了，诊断价值也用不上 |
| 5 | WinRT 套接字 | 只到「已连接」无音频，释放即断；32feet 维护者明确不推荐 [社区实测] |
| 6 | PnP 禁用再启用 | 需要管理员，等于重装设备栈 |

要点：

- `KSPROPERTY_ONESHOT_RECONNECT` 成功只表示驱动尝试过，不代表连上；官方建议用插孔描述核实端点。本项目发的是 `KSPROPERTY_TYPE_GET`，与文档和 ToothTray 一致。[官方文档] [源码确认]
- 没有任何资料解释「A2DP 卡在已配对而 HFP 先拉起链路」的栈内原因，只有间接证据。[推测]
- Windows 11 把端点合并成一个，枚举必须包含采集方向，否则会漏掉 HFP 过滤器、断开时麦克风还连着。[作者声明] [issue 用户报告]
- 本机的 BTHUSB Event ID 3 是适配器 HCI 命令超时警告，没有官方根因文档；它同时拖慢系统设置里的连接。[issue 用户报告]

## 5. 连不上时的自救清单（只列有来源的）

1. 耳机关机几秒再开机，确认在范围内。[官方文档]
2. 关闭电脑蓝牙，等 10 秒再打开。[官方文档]
3. 把适配器移离 USB 3.0 设备，换 USB 2.0 口或 USB 2.0 hub。[官方文档] [社区实测]
4. 笔记本自带蓝牙又插了适配器时，只保留一个。[社区实测]
5. 设备管理器里取消适配器的「允许计算机关闭此设备以节约电源」。[官方文档]
6. 重启 Bluetooth Support Service。[官方文档]
7. 连上但没声音：确认输出选的是耳机的 Stereo 而不是 Hands-Free，格式设为 2 声道 16 位 48000 Hz。[官方文档]
8. 同一时段系统日志里有 BTHUSB 事件 3 / 5 / 17 时，提示这是适配器或 USB 链路问题。[issue 用户报告]

## 6. 生态位

- 做最稳、最轻的一键连接：不要管理员、不装驱动、HFP 优先。
- 把零驱动能做的做满：通话保音质引导、免提开关、BLE 电量与入耳。
- 对国内用户友好：更新与下载走可用线路（直连 GitHub 在国内基本不可用）。
- 隐私与诚实：不采集原始设备标识，不把失败写成通过。
- 中期护城河：正规签名的 AAP 驱动。
