# 技术方案（架构、选型与关键决策）

现状：稳定；反映 1.9.40 源码 ｜ 负责人：项目维护者 ｜ 最后更新时间：2026-11-25

读这份文档的时机：做技术决策、升级依赖、想知道「为什么这么选」。实现细节在 [02-架构与原理](02-架构与原理.md)，连接策略在 [09](09-Windows连接方案选型.md)，更新事务在 [08](08-更新与后台任务.md)。带日期的早期方案（NavigateToString、WMI 查音频、v1.9.16 切默认设备）已归档到 [技术方案历史](../reference/history/tech-decisions-202609.md)，不是当前部署指令。

## 一句话架构

AutoHotkey v2 宿主负责托盘、窗口和状态机；界面是内嵌的 WebView2 页面；蓝牙与音频操作交给 PowerShell 子进程里运行时编译的 C#（MMDevice 拓扑 + KS 属性 + Core Audio）。不装驱动、不要管理员、不碰配对。

```
托盘 / 快捷弹层 ─┐
主窗口 (WebView2) ┼─ airpods_buddy.ahk ── RPC 白名单 ──┬─ BackgroundJobs → powershell 子进程
右下角小精灵 ──────┘   每设备状态机 / 代次 / 路由所有权  │    ├─ KsBluetooth.cs  连接 / 断开 / 链路查询
                                      │                 │    ├─ Core Audio      端点状态 / 默认设备
   lib/Diagnostics.ahk 脱敏日志 ←─────┘                 │    └─ UpdateCore      查新 / 校验 / 事务替换
                                                        └─ 本机设置 app_settings.ini（原子写）
```

## 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 宿主 | AutoHotkey v2 x64 | 单文件 exe；`tools/ahk_v2_portable` + Ahk2Exe 1.1.36.02f |
| 界面 | WebView2 + 原生 HTML/CSS/JS | 无框架；页面与图片内联后约 0.84M 字符 |
| 后端 | PowerShell 5.1 + 运行时编译 C# | `Add-Type` 编译 `KsBluetooth.cs`，无需随包带二进制 |
| 音频 | Core Audio（MMDevice、IPolicyConfig） | 默认设备三角色切换与读回 |
| 更新 | GitHub Release API + SHA-256 + `File.Replace` | 见 [08](08-更新与后台任务.md) |
| 测试 | Python 驱动的离线套件 | `.py` / `.ps1` / `.ahk` / `.cjs`，不连真机 |
| 实验室 | .NET 8 WinForms（自包含） | `beta/`，独立安装目录 |
| Mac | Swift | `mac/`，独立 CI |

为什么是 AHK v2 + WebView2：体积小、依赖只有系统自带的 Edge 内核、界面表现力足够；纯 AHK 控件做不出米白毛玻璃，Electron / Tauri 对一个托盘小工具太重。

## 关键设计决策

| 决策 | 没选什么 | 原因 |
|---|---|---|
| 用音频端点 KS 过滤器的 `KSPROPERTY_ONESHOT_RECONNECT` 触发连接 | 上游的 `BluetoothSetServiceState`、WinRT 套接字、PnP 禁用再启用 | 不要管理员、不重装驱动、没有 1.28 秒发现等待；WinRT 套接字只能到「已连接」而没有音频端点，PnP 开关需要管理员。做法参考 ToothTray（BSD-2）与 BTAudioSysTrayTool（MIT），见 `THIRD_PARTY_NOTICES.md` |
| 目标身份用「设备容器 → 精确端点 ID → KS 过滤器 ID」三重绑定，发请求前再核对一次 | 按设备名或「Stereo / Hands-Free」字样猜 | 同一副耳机会暴露多个端点，名字有歧义；拓扑在列出和发送之间可能变化 |
| AirPods 冷连接先对免提（HFP）过滤器发一次请求，再等立体声端点自己激活 | 只请求立体声端点 | 在通用 USB 适配器 + 微软通用驱动的机器上，立体声请求被接受却建不起链路；HFP 请求 1–2 秒建立链路，立体声随后激活。条件：AirPods、未开麦、链路已确认断开、立体声端点 UNPLUGGED、同容器内 HFP 渲染/采集端点唯一。其他设备保持原策略，见 [09](09-Windows连接方案选型.md) |
| 证据分层：请求回执 ≠ 链路 ≠ 端点 ACTIVE ≠ 默认输出 ≠ 实际听音 | 以 API 返回成功当作「已连接」 | 微软文档明确 ONESHOT_RECONNECT 成功只表示驱动尝试过；用户反馈里大量「已连接但没声音」都出在这一层 |
| 所有操作有界：同目标最多再试一次，观察窗口有限，取消和忙碌都有终态 | 无限重试、后台自动重连 | 不打扰用户，不给系统蓝牙栈叠加压力 |
| 默认不切换麦克风（`auto_mic_switch=0`），只撤回自己确实改过的角色 | 连接即切默认麦克风 | 普通听歌用户不应该被悄悄换掉默认麦克风； Classic 蓝牙用耳机麦就会掉到电话音质 |
| 通话进行中不做播放探测 | 每 30 秒初始化一次播放流核实 | 探测本身可能扰动通话；改为只读录音会话状态 |
| 页面用 WebView2 虚拟主机映射加载 | `NavigateToString` | 后者有 2MB 上限，且导航来源是内部 data URL，无法按来源拦截 |
| 整窗开盒动画用根窗口透明色键 + CSS 后转轴透视 | 分层窗口 / 视频运行时 | 实现简单、CPU 开销低；不捆绑视频运行时 |
| 小精灵用四张独立 7×7 精灵表（共 196 帧），128px 格、20fps，脚底对齐 | 一张长表或逐帧加载 | 每张表一个动作语义（戴上、摘下、检查、等待、待机），不出现静止帧；隐藏时停止合成 |
| 托盘弹层用共享 WebView2 环境的独立控制器 | 原生菜单 | 可以做毛玻璃与品牌视觉；原生菜单保留为故障回退 |
| 日志先进有界队列再批量落盘，按大小轮转，保留七天 | 逐条追加 | 不阻塞界面，控制磁盘占用；错误只写日志不弹窗 |
| 反馈日志默认脱敏并匿名化设备 | 原始地址与端点 ID | 设备地址、端点、路径属于可识别信息；用户勾选才附日志 |
| 更新走「元数据校验 → 下载校验 → 暂存 → 原子替换 → 健康回执 → 失败回滚」 | 直接覆盖 exe | 任何一步失败都保留可运行的旧版；新版确认健康后才清理旧回退副本 |

## 资源与耗时（本机实测口径）

- 启动：从进程启动到窗口可见约 1 秒（含 WebView2 环境创建）。
- 连接：HFP 引导后 1–2 秒链路建立；立体声端点在数秒到近 30 秒内激活，之后才做播放预检和默认输出切换。
- 空闲：主窗口隐藏后小精灵停止合成；托盘图标只在状态变化时重绘。

## 约束

- 构建前必须先跑 `webui/build_ui.ps1`，否则 exe 里是旧页面或旧图。
- `build-manifest.json` 记录全部输入哈希，打包脚本拒绝与当前源码不一致的构建。
- 构建产物只保留最新两个；安装目录只保留最近几份回退副本。
