## 公开发布前的离线预检

有两个显式档位，绝不可混淆。下段是**严格五轮通过档位**：只有真实五轮完成才能生成 `gate-pass.json`。2026-09-27 用户选择的 v1.9.20 是**接受已知问题档位**，下方另述；该档位不生成/不借用五轮通过回执，历史失败仍作为失败保留。

Windows CI 只运行离线回归与 build-only，不运行真实耳机，也不上传资产。真实发版前先在隔离设置下运行 `python tests/strict_gate.py --address <12位目标地址> --settings <仓库内micOff设置文件> --cycles 5 --dwell 15 --release-gate --output <新的仓库内证据目录>`；此路径不改写生产重试函数，首错即停，只有完整五轮成功才生成 `gate-pass.json`。回执绑定运行时源码、设置、逐阶段结果及各阶段原始日志 SHA256；诊断用 `--single-request` 明确被发布门槛拒绝。

用最终源码执行 `scripts/build-deploy.ps1` 的 build-only，依据该构建产物制作精确命名的 `AirPodsBuddy-Windows.zip`。安装候选后，再独立完成人工验收回执 `installed-acceptance.json`：`installedExePath` 指向实际运行的安装 exe，`installedExeSha256` 与最终构建一致，`gateResultsSha256` 绑定本次生产五轮结果；`checks` 中的 `restartReconnect`、`defaultOutputListening`、`micOn` 均需 `passed:true`、同目录证据文件名 `evidence` 与对应 `sha256`，听音还需 `userConfirmed:true`，micOn 需 `autoMicSwitch:"1"`。回执应在真实重启复连、默认路径听音及 micOn 检查后由验收人填写，预检不自动生成成功回执。上传前运行 `python scripts/release-precheck.py --gate-dir <通过的证据目录> --build-dir <最终构建目录> --zip <最终AirPodsBuddy-Windows.zip> --acceptance <installed-acceptance.json>`；预检要求生产五轮 31 阶段、最多一次有界连接重试，当前源码/构建/ZIP 内 exe 一致，安装版及三项人工验收证据哈希一致。预检只验证提交证据的内部一致性，**不自行证明人工回执所述听音或操作真实发生**；验收人仍须核对原始记录与用户确认。预检输出 ZIP SHA256 供上传后与 GitHub 资产 digest 交叉核对；缺任一项即不能按**严格五轮档位**发布。

接受已知问题档位的命令为 `python scripts/release-precheck.py --accepted-known-issue --failure-dir <历史失败证据目录> --known-issues RELEASE_NOTES_v1.9.20.md --build-dir <最终构建目录> --zip <最终AirPodsBuddy-Windows.zip> --acceptance <已知问题人工回执.json>`。此路径保留 `hardwareGate=failed`：核对历史 `results.json` 中成功基线与随后非零连接/断开结果、失败文本及日志哈希、明确项目所有者的正式发版决定、已知问题文案哈希、最终安装 exe 与构建/ZIP 哈希相同，以及最终安装版启动、默认输出**用户听音确认**、反馈入口三项独立证据。预检的 `HUMAN_ATTESTATION_NOT_MACHINE_VERIFIED` 明示只校验回执文件与哈希，不凭脚本证明用户真的听见；验收人必须核对原始答复。历史失败可以来自旧候选，但回执必须写明 `failureEvidenceHistorical=true` 和来源哈希，不能冒充最终构建复测。严格路径原样保留。

最终 build-only 目录确定后，用 `python scripts/package-windows-release.py --build-dir <最终dist/build-...目录> --output-dir <新的输出目录>` 离线制作资产。输出目录必须尚不存在；脚本核对 `build-manifest.json` 所列全部编译输入与当前源码树清单、版本、源文件哈希及 exe 哈希，打包后再次核对以拒绝构建漂移；ZIP 只含根目录 `AirPodsBuddy.exe`，并读回验证 CRC、exe SHA256 与构建清单一致。它不编译、不部署、不上传；已有输出拒绝覆盖。完成后仍须执行所选档位的安装版人工验收与 `release-precheck.py`；严格档位需完整生产五轮，接受已知问题档位需可核验的失败证据与公开披露。不能凭 ZIP 制作成功宣布可发布。

上传前预检也要求 ZIP **唯一**条目就是根目录 `AirPodsBuddy.exe`；有额外目录或文件的包会拒绝，避免打包器正确而预检放过其他工具生成的杂项资产。

## 修改原因
旧更新器直接接受网页 URL，同步下载，固定临时目录、未检查 tar 退出码、脚本追加且无版本健康回滚。旧反馈把 no-cors opaque 响应当送达，蓝牙与网络阻塞宿主。

## 更新事务
1. 宿主仅接受无参数 doupdate；后台重新请求指定 GitHub 仓库的 latest API。
2. 拒绝 draft、prerelease、不合法版本、其他域名/仓库、多个同名资产和缺失 SHA256 digest。没有可信摘要的历史发布包保留手动发布页，不盲目执行。
3. 下载到本任务唯一目录（90 秒网络超时、120 秒总截止），先核对摘要，再校验 ZIP 所有路径、总解压大小、symlink 和根 exe。只提取指定 exe。
4. 新文件复制到安装目录旁，核对复制哈希；原子 Replace 同时保留旧 exe，记录原始哈希，核对备份哈希。
5. 新进程收到唯一健康令牌。主 WebView 导航成功才写版本标记；继续存活三秒并复核版本后才提交成功回执。
6. 健康失败或异常恢复旧 exe，并按替换前哈希验收。备份损坏时明确 ROLLBACK_FAILED，不宣称恢复成功、不重启未知字节。
7. 新进程轮询更新回执，覆盖慢启动，避免仅启动 3.5 秒读取一次造成提示丢失。

这里使用 GitHub API 提供的资产摘要作为完整性来源，并未宣称 Authenticode 签名或私钥已配置。公开发版仍需用户明确同意。

## 后台任务
请求 JSON 与结果文件放独立任务目录，网页既不指定 worker 路径，也不传任意命令。
宿主持有实际进程句柄；退出/超时终止自己拥有的进程，不依赖可能复用的 PID；回调后关闭句柄并清理目录。
反馈全程只有一个在途事务，前端截止晚于 worker 的总截止；HTTP 2xx、进程退出码零均不替代业务 errcode=0。
降噪和 KS 蓝牙调用也走子进程。v1.9.20 移除服务安装/移除后端；worker 回传 backend=ks、ContainerId、render/capture ID、请求数量。请求数为零只代表已激活时复用连接，不代替真实链路/音频核实。宿主验证字段后才推进状态机。打包清单包含 KS 源码、模块与第三方版权。

## 实测结论
- 真实部署时，第一包的导航规则误拦 WebView 内部 data URL，健康检查失败后旧 v1.9.17 被恢复并重新启动；这次失败被保留在日志中。
- 换成精确虚拟主机 URL 后，v1.9.19 导航、RPC 和三秒存活健康检查通过。
- 故障注入覆盖摘要不符、外部 URL、缺失 digest、ZIP traversal、非 PE、健康失败/异常、回滚内容核对、HTTP 业务拒绝、目标录音端点误判、finally 恢复设备。
- 测试未向真实反馈群发送试验数据，也未执行全局音频服务重启或自动蓝牙 radio reset。

## 最终复核追加
- 已退出worker优先读取结果，UI迟轮询不误报超时；合法业务结果不残留缺失回执错误。
- 健康检查异常由finally终止新子进程；失败回执写拒绝不阻断原始hash核对与旧版重启。
- 构建清单覆盖全部编译输入与工具hash，编译后和部署前复核；元数据复制错误不冒充应用回滚。
- 对应后台5项、健康异常3项回归通过。
